# Audit before v1.0.0

November 2026, on `main` after M7. This is the final audit of [the spec](../spec.md#quality):
fuzzing of the parsers, a threat review of what touches other apps, the network and code, and the
performance budgets measured on a release build. What it found is fixed in the same change unless
it says otherwise.

## Fuzzing

Each fuzz target feeds a parser what the user, another app, a file or a process could give it,
and asserts that it answers or refuses without panicking, hanging or allocating without bound.

| Target | What it reads |
|---|---|
| `calc.FuzzEval` | Anything typed in the root search, both languages, with currencies |
| `config.FuzzParse` | settings.toml |
| `theme.FuzzLoad`, `theme.FuzzParseColor` | A user's theme file; colors, which must survive their hex |
| `hotkey.FuzzParse`, `ui.FuzzParseAccelerator` | Hotkeys in the settings; action shortcuts |
| `tomlpos.FuzzParse` | TOML read with positions, for the settings' problems |
| `scripts.FuzzParse` | A Script Command's metadata comments |
| `ai.FuzzParseCommand` | An AI Command file |
| `translator.FuzzExchange` | The translation engine's answers on its pipe |
| `clipboard.FuzzThumbnail` | An image copied by another app |
| `foldersync.FuzzJoin` | A sync folder's header, which any program with the folder can write |

Run one with `go test ./internal/config -run '^$' -fuzz FuzzParse -fuzztime 1m`. Their seeds run
with every `go test`.

Each target ran 45 seconds on Windows, four workers, after the fixes below: no failure. Most ran
hundreds of thousands to millions of inputs; `FuzzJoin` ran 149, since each header that passes
the checks derives a key with Argon2id, as it should.

## Threat review

### Found and fixed

1. **Script Commands: PowerShell argument injection (high).** Arguments typed for a `.ps1` script
   were quoted by doubling the ASCII apostrophe only, but PowerShell also takes `‘ ’ ‚ ‛` as single
   quotes: `x’; calc; ’` ended the string and ran `calc`. Every one of them is now doubled
   (`TestPowerShellArgumentsStayArguments`).
2. **Script Commands: batch argument injection (high).** `cmd.exe` parses a command line by its own
   rules, not those Go quotes arguments by, so an argument such as `a&calc` given to a `.bat` or
   `.cmd` script ran `calc`. Arguments with `" % ! ^ & | < >`, a line break or NUL are now refused
   with an error (`TestBatchArgumentsCannotRunCommands`).
3. **Clipboard history: decompression bomb (medium).** A copied image was decoded whole for its
   preview: a small PNG claiming 50 000 × 50 000 pixels would have allocated about 10 GB. The size
   is now read first, and images over 8192 × 8192 are kept without a preview.
4. **Translator: unbounded answer (low).** The engine's answer header gave a length that was
   allocated as is; it is now capped at 16 MB.
5. **Calculator: stack exhaustion (low).** The parser recurses per parenthesis and power, and Go
   cannot recover from a stack overflow. Expressions of more than 256 tokens are refused.
6. **Sync: costly key derivation (low).** A sync folder's header could ask Argon2id for up to 1 GB
   and 20 passes. It is now limited to 256 MB and 10 passes, four times Althea's own.
7. **Idle CPU (budget).** Sync ran on a one-minute ticker even while nothing happened. It now runs a
   few seconds after something may have changed and never on a timer.
8. **Dependencies.** `golang.org/x/net` and `golang.org/x/crypto` raised to their fixed versions.
   `govulncheck` reports nothing Althea calls; the one advisory left, GO-2026-5932, is about
   `x/crypto/openpgp`, which Althea does not import.

### Reviewed, nothing to fix

- **Keyboard hook.** Snippet expansion keeps only the end of what was typed, no longer than the
  longest keyword, clears it in password fields, and logs nothing typed. The Win-key hook only
  watches for the key alone.
- **Clipboard.** Contents are sealed with AES-GCM under a key in Credential Manager; copies marked
  `ExcludeClipboardContentFromMonitorProcessing`, `Clipboard Viewer Ignore` or
  `CanIncludeInClipboardHistory = 0`, as password managers mark them, are never kept. Retention
  prunes on its own. Clipboard history never syncs.
- **Downloads.** The translator's engine and models come from URLs pinned in the code, are limited
  to their expected size, verified by SHA-256 before they are moved into place, and the engine's
  hash is checked again before each start.
- **Network.** Every request goes through `internal/netpolicy`, which refuses those not made for
  something the user did and logs each with its method, host and path, never its query string or
  body, where search terms and keys would be.
- **AI.** The selection or clipboard goes to the configured provider only when the user runs a
  command; keys stay in Credential Manager. A model's answer is shown as Markdown whose links
  open only through MyGo's `SafeToOpen`, or pasted as text: nothing it says is run.
- **Sync.** Every computer's file is sealed and bound to its device ID, so a file renamed to pass
  for another's is not read. Records are written only through their source: file names are
  checked to stay inside their folder (`TestFileSourceStaysInItsFolder`). Scripts, which run code,
  are not among what syncs; neither are the vault's secrets.
- **Notes.** Sealed at rest with a key in Credential Manager.

## Performance budgets

Measured with `internal/soak` on a release build (`-trimpath -ldflags "-s -w -H windowsgui"`),
a portable copy started as at login, three cold starts after a first one, on the development
laptop (Windows 11, 2026-11-06):

| Metric | Budget | Measured |
|---|---|---|
| Cold start to ready | < 300 ms | 266 ms median (243 ms of it inside `app.Run`) |
| Idle memory | < 60 MB | 34.9 MB private working set |
| Idle CPU | ~0 % | 0 to 0.16 % over 10 s, one garbage collection after the start |
| Keystroke to results, 10 000 items | < 16 ms p95 | held by `TestRankBudget` and `TestQueryBudget` on every CI run |
| Hotkey to visible window | < 50 ms p95 | to measure: `go run ./internal/soak -exe althea.exe -hotkey` |
| Animations and scrolling | 60 fps | checked by eye in the real window |

The first measurement copied the executable anew for each start and showed it: about 1.1 s and
83 MB. The second measures what users get: the antivirus scans a new executable once, and the
launcher is hidden until the hotkey. `-hotkey` presses Alt+Space thirty times and also reports
the idle memory after the launcher has shown, which is what an Althea in use sits at.

Idle means after start-up work: in the first seconds File Search indexes the user's folders, and
a measurement 5 s after ready read 23 % CPU, back to 0 % by 15 s.

The first soak runs also left their copy, in a temporary folder, at Windows' startup, since start
at login is on by default; Microsoft Defender flagged that as `Behavior:Win32/Persistence.A!ml`, an
unsigned executable in a temporary folder adding itself to the Run key. The soak now turns start
at login off in its copy. The same heuristic is a reason to install to a fixed folder and to sign
the executable, as the release plans.

## Soak test

`internal/soak` runs a portable copy for hours, showing and hiding the launcher, and samples its
private working set, private bytes, handles, GDI and USER objects and threads to a CSV:

    go build -trimpath -ldflags "-s -w -H windowsgui" -o althea.exe ./cmd/althea
    go run ./internal/soak -exe althea.exe -soak 24h -csv soak.csv

To run before v1.0.0: the report compares the first sample after warm-up with the last, and the
CSV shows any growth of memory, handles or GDI objects over the day.
